## Part A — Counter A: why the terminal app disappeared

**Investigate first, then fix.** In the report, explain the most likely cause with evidence. The likely causes, in order:

1. **A failed update.** If the Tauri updater runs the NSIS installer in "uninstall, then install" mode and the install half fails (Defender blocks it, the PC loses power, or the update download was incomplete or blocked), the result is exactly an **empty install folder**. Check how the updater replaces files, and look at the update logs and the server's update records for Counter A.
2. **Antivirus quarantine.** Defender flagged an unsigned Tausi installer earlier. If Defender quarantined `tausi-terminal.exe` or its files, the folder would empty out. The owner will check Windows Security → Protection history (see `docs/TROUBLESHOOTING.md`).
3. **An uninstall,** run by a person or by the installer itself on a failed upgrade.

**Fixes, whatever the cause:**
- **Safe updates for the terminal:**
  - Download the update to a temporary folder and **check its signature and checksum** before touching the installed app.
  - Install it **side by side**: new files into a new folder, then switch over once complete. Keep the previous version until the new one has started successfully once.
  - **If the new version doesn't start** within 60 seconds, roll back to the previous one by itself.
  - Never leave the install folder empty. If that would happen, don't uninstall.
- **Self-repair launcher:**
  - Add a tiny **launcher** (a separate small `.exe`, installed in its own folder), used by the shortcuts and autostart, which starts the app.
  - If the app is missing or broken, it shows "Tausi POS needs repairing" with **Repair**, which re-downloads the matching terminal installer **from the paired server** (the server already holds it, as in Task 15) and reinstalls it, keeping the pairing.
  - This also covers the watchdog and shortcut items sent earlier: it restarts the app if it exits unexpectedly, and recreates missing shortcuts and autostart.
- **Keep the pairing outside the install folder.** The device token and settings live in `C:\ProgramData\Tausi POS\Terminal\` (or the user's app data folder, protected with DPAPI), so a reinstall or repair **keeps the pairing**. Check that this is already true, and fix it if not.
- **Report to the server:** each terminal reports its app version, the result of its last update (success, rolled back or failed, with the error), and its last exit reason. Show these on the **Terminals** page, with a warning such as "Counter A: last update failed (blocked by antivirus)".
- **Defender:** in `docs/TROUBLESHOOTING.md`, add how to check Protection history, restore a quarantined file, and submit a false-positive report. Self-signed signing (if it's set up) makes this less likely, and the docs should say so.

**Tests:**
- an update interrupted part-way (simulated) leaves the old version working
- an update that fails to start rolls back
- the launcher repairs a missing app from the server, and the pairing is kept
- shortcuts are recreated
- the Terminals page shows the update result and exit reason


## Part B — Date-based reporting (sale date, not work-period date)

**The problem:** Task 12 gave every entry the **business date of its work period**, meaning the date it was opened. If a work period opened on Sunday is still open on Wednesday, Wednesday's sales show as Sunday's.

**The new rule: each transaction has its own sale date.**
- **Sale date:** for every **ticket line, payment, settle, void, gift, discount, pay-out, cash drop, stock movement and journal entry**, the sale date (still called the **business date**) is simply the **calendar date when it happened**, in `business.timeZone`, with the day changing at midnight. A sale at 10:00 on Wednesday counts as **Wednesday**, and a sale at 01:30 on Saturday counts as **Saturday**, whichever work period is open. There's no day cut-off setting (the owner's decision).
- **Settled tickets:** the ticket's date for "sales" reports is the date of **each line's print time** (when it was served), and payments use the date they were taken. So a ticket opened on Tuesday night and paid on Wednesday morning puts its items on Tuesday and its cash on Wednesday. Use the same rule in the ledger, so reports and the books still agree.
- **Admin-site entries** (expenses, deliveries, banking and so on) keep the date chosen on the form, as now.
- **Migration:** recalculate the business date of existing rows from their timestamps. Write the old value to a backup column for one release, so it can be checked. It runs on both providers, in batches, and is safe on a large database.

**Reports:**
- **Every report's main filter becomes dates,** on the admin site: Today / Yesterday / This week / Last week / This month / Pick dates.
- **"By work period"** stays as a **secondary** filter, for the Z report and cash-ups. A note explains: "Work periods can span several days. Use dates to see each day's sales."
- **The Z report** (close day) still covers its whole work period, but **splits the figures by date** when the period covers more than one day, with a warning line: "This work period covered 3 days (Sun 2 – Tue 4 Nov)."
- **Cash-up** stays per cashier shift, but its slip shows the date range the shift covered.
- **Agreement tests (Task 13):** they must still pass with date filters, so daily totals add up to the period total, and reports equal the ledger for every date.

**Closing doesn't change.** There are no new reminders or banners for long-open work periods or shifts (the owner's decision, for now), and nothing closes automatically. Closing still follows the "no open tickets" rule. Record this in DECISIONS.md as a possible follow-up.
