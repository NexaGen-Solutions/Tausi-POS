## How it fits together

- **The bar's server is on the local network,** and Safaricom can't reach it. So a small **Tausi relay**, hosted by NexaGen on the internet, receives Safaricom's messages. Each bar's server **connects out** to the relay to collect its own payments. Nothing is opened in the bar's firewall.
- **Payments are applied by people.** Payments arrive on the settle screen and are added to a bill automatically (STK, or a QR that matches its bill) or picked by the cashier. **The cashier still presses Complete**, so the owner's rule stays: only the cashier settles.
- **The internet is optional for trading.** When the internet or the relay is down, the bar keeps trading, and cashiers type codes as in v1.0.

**Owner's decisions** (put them in DECISIONS.md):
- Waiters **can** send prompts. It's a setting, **on by default**, that can be turned off.
- The QR prints on **every bill**. It's a setting, **on by default**, that can be turned off.
- A payment that covers the bill **doesn't** settle it by itself. The cashier presses Complete.
- The server collects payments from the relay **only while there are open tickets**, plus catch-up collections (Part B).
- There's an **M-Pesa ledger** of applied and unapplied payments (Part F).

## Part A — The Tausi relay (new service)

**Where it lives:** a new project, `relay/Tausi.Relay`, a small .NET minimal API with PostgreSQL. It's built in CI as a Linux container image and a tarball, and is **not** part of the bar installers. It's hosted by NexaGen, for example at `pay.nexagensolutions.com`.

**Businesses:**
- Each business that uses M-Pesa gets a relay account: a business id, an **API key** (shown once, stored hashed) and an unguessable **callback path token**.
- A small NexaGen-only admin page (protected by a NexaGen login) creates accounts and shows each account's last seen time and payment counts.

**Callback endpoints**, one set per business, using its path token:
- `POST /mpesa/{token}/stk`: STK push results
- `POST /mpesa/{token}/c2b/validation` and `/c2b/confirmation`: till and paybill payments, including QR payments
- Accept requests only from **Safaricom's published callback IP ranges** (kept as a configurable list) **and** with a valid token. Log and refuse everything else.
- Respond to Safaricom quickly with the response format Daraja expects. Validation always accepts in v1.1.

**Storage:**
- Each payment is stored per business, keyed on the **M-Pesa transaction id**, so a repeated callback is stored once.
- It's held until the bar's server **acknowledges** it, then kept for 30 days for reference, then deleted.

**Delivery to the bar:**
- The bar's server connects out with its API key, over a WebSocket (or long-poll HTTPS as a fallback).
- On connecting, it receives every **unacknowledged** payment, then new ones live.
- It acknowledges each one after saving it in its own database.

**Isolation:** a business can **only** ever receive its own payments, with tests that prove it.

**Operations:**
- `docs/RELAY.md` covers hosting (TLS, PostgreSQL, backups, health endpoint, logs), adding a business, rotating a key, and updating Safaricom's IP list.
- No customer card or PIN data ever passes through it. Phone numbers are stored **masked**, except where Safaricom's matching needs the full number, and then encrypted.

## Part B — Connecting the bar's server to Daraja and the relay

**Settings → M-Pesa** (board 26), in the Task 10 registry. It needs `settings.manage`.
- **Type:** Buy Goods (Till) or Paybill.
- **Numbers:** the till number, or paybill number. For Buy Goods, also the **store number** (head office short code), which Daraja's STK push needs as `BusinessShortCode` while the till number is `PartyB`. Explain this in the help text.
- **Credentials:** the Daraja consumer key and secret, and the STK **passkey**, all **encrypted** and never returned by the API (shown as `••••` with **Change**).
- **Environment:** Sandbox or Live.
- **Relay:** the relay address and the business API key, shown as `••••`.
- **Rules:**
  - `mpesa.stkEnabled` (on)
  - `mpesa.waiterPrompts` (on)
  - `mpesa.qrOnBill` (on)
  - `mpesa.allowTypedCodes` (on)
- **Test connection** gets a Daraja OAuth token, checks the relay login, and (on first set-up) **registers the C2B URLs** with Daraja for this short code, pointing at this business's relay callback paths. Show each check with ✓ or a plain error.

**When the server collects payments from the relay:**
- **It stays connected while any ticket is open** in an open work period, and disconnects when there are none.
- **Catch-up collections:**
  - when the day is **opened**
  - just **before Close day** finishes, which must wait for it or time out after 15 seconds with a warning
  - when an admin presses **Fetch payments now** on the ledger page
- Nothing is lost while disconnected, because the relay holds payments until they're acknowledged.
- The connection status shows on board 26: "Connected", "Not connected (no open tickets)", or "Can't reach the relay" with the reason.

## Part C — STK prompt (send a PIN prompt to the customer's phone)

**On the settle screen** (boards 22 and 23): the M-Pesa tab gets three choices: **Send prompt to phone**, **Payments received (n)** and **Type a code**.

**Send prompt:**
- **Phone number:** accepts `07…`, `01…`, `+254…` and `254…`, and normalises to `2547…` / `2541…`.
- **Amount:** defaults to the **remaining** amount, and can be lowered for split payments. It can't be more than what's remaining.
- **One active prompt per ticket.** A second one asks "Cancel the waiting prompt and send a new one?"

**Waiting** (board 23, left):
- A timer counts up.
- **Send again** and **Cancel**.
- It expires after 2 minutes.

**How the result arrives, by two routes:**
- the relay's STK callback, **and**
- **asking Daraja with the STK Query API** every 5 seconds while waiting (an outgoing call), so STK still works if the relay is unreachable.

Whichever answers first wins, and the other is ignored by the transaction id.

**Results, in plain words:**
- **Paid:** board 23, right side, green.
- **Cancelled by the customer.**
- **Not enough money.**
- **No response from the phone.**
- **Wrong PIN**, and anything else, mapped from the Daraja result codes.

**On success:**
1. Create an `MpesaTransaction`, which is **confirmed**, since it came from Safaricom.
2. Add a **pending payment** of that amount to the ticket (Task 8), with **brought by** = the user who sent the prompt if it was a waiter, otherwise the waiter who opened the ticket. The cashier can change it.
3. Mark the transaction **Applied**, and publish `ticket.changed`.
4. **The cashier still presses Complete.**

**From the order screen** (board 25): when `mpesa.waiterPrompts` is on, the order screen has **Ask for M-Pesa payment** for any user who can open the ticket. It uses the same dialog and flow. The waiter sees "Paid ✓ KSh 1,370", and on the map the table shows "M-Pesa received", so the cashier knows to settle it.

**Permissions:**
- Sending prompts from the settle screen needs `ticket.settle`.
- Sending them from the order screen needs `order.add` plus the setting.
- Every prompt is audited, with who sent it, the ticket, the phone number (masked) and the amount.

## Part D — The QR code on the bill

When `mpesa.qrOnBill` is on, every **bill** (not the receipt) gets the board 26 section:
- **"SCAN TO PAY WITH M-PESA"**
- the **QR code**, from Daraja's **Dynamic QR API** for the bill's amount, with the ticket number as the reference
- "Till 123456 · KSh 1,370 · #1042"
- "Or pay to Till 123456 and show the message to your waiter"

**Generating it:**
- The QR is generated when the bill prints, cached per bill number, and printed as a 1-bit raster at the same width rules as the logo.
- **If Daraja doesn't answer within 3 seconds, or there's no internet,** the bill prints **without** the QR, with just the till line. **Printing a bill must never wait longer than that for M-Pesa.**

**Matching QR payments to their bill:**
1. **Check first:** find out from Daraja's documentation and a sandbox test whether the C2B confirmation for a QR payment carries the **reference** (the ticket number) for **Buy Goods** and for **Paybill**. Write the findings in DECISIONS.md.
2. **If the reference comes back,** match it **exactly** to the ticket, and add the payment to that ticket as a pending payment, as STK does (board 24, "QR on this bill").
3. **If it doesn't** (or for payments typed into the till by the customer), the payment goes to **Payments received**, where it's **suggested**:
    - "Same amount" when the amount equals an open ticket's remaining amount and a bill was printed in the last 30 minutes.
    - **Never apply a payment automatically on amount alone.**
4. **For Paybill,** the account number the customer types is matched to a ticket number when it's exact.

## Part E — Payments received, typed codes, and partial use

**`MpesaTransaction`:**
- transaction id (unique)
- amount and **amount applied**
- payer name, masked phone
- time
- short code
- bill reference
- source: `Stk`, `C2B`, `Typed`
- status: `Unapplied`, `PartlyApplied`, `Applied`, `NotFromPos`
- links to the payments that used it
- confirmed (yes/no)

**Payments received list** (board 24): the cashier's live list of **Unapplied** and **PartlyApplied** transactions from the last 24 hours, with matches highlighted and **Add to this bill**.

**Partial use:**
- A transaction bigger than the remaining amount is applied **only up to the remaining amount**, and the rest stays available, as **PartlyApplied**, for another bill.
- An M-Pesa payment never gives change.

**Typed codes** (when `mpesa.allowTypedCodes` is on):
- **If the typed code is already in `MpesaTransaction`:** it uses that transaction, which is confirmed, and applies it as above.
- **If it isn't:** the payment is saved as **unconfirmed**, as in v1.0. When a relay payment with that transaction id arrives later, it's **linked and confirmed** automatically.
- **Still unconfirmed after 24 hours,** it's flagged **"Typed, never confirmed"** in the ledger. That's the fake-SMS warning.
- The v1.0 rule that a code can be used only once still applies across typed and received payments.

## Part F — The M-Pesa ledger (board 27)

**Where:** the admin site, at **M-Pesa payments**, in the sidebar after the Cash book. It needs `reports.all` or `cash.book`. It also appears on the terminal's Reports screen (Task 17b) for `reports.all` users, as a **read-only** list.

**Filters:** dates (as in 17a), status, source, and "only problems" (unapplied and never-confirmed).

**Tiles:**
- **Received**
- **Applied**
- **Unapplied**, in orange
- **Not from POS**
- **Typed, never confirmed**, in orange

Each shows a count and an amount.

**Rows:** time, code, from, how (STK prompt / QR on bill / Paid to till / Code typed), amount, status with the ticket, receipt and cashier when applied.

**Actions:**
- **Apply to ticket** (needs `ticket.settle`): pick an open or part-paid ticket. It adds a pending payment, and the cashier completes the ticket as usual.
- **Mark as not from POS** (needs `cash.book`): a reason is required, plus a choice of account: **Other income** or **Owner's capital**. It posts a balanced entry, debit **M-Pesa**, credit the chosen account, on the transaction's date.
- **Check** on a never-confirmed typed code: opens the ticket detail (Task 13), so a supervisor can investigate.

All actions are audited.

**Fetch payments now** runs a catch-up collection from the relay.

**Export to Excel**, in the Task 13 format, for checking against the Safaricom till statement.

**Close day:** the Close day screen shows "3 unapplied M-Pesa payments · KSh 2,870" as a **warning, not a block**, with a link to the ledger.

**Ledger accounting:** applied payments post through settling, as in v1.0 (debit M-Pesa at settle). Unapplied payments **aren't** posted until they're applied or marked "not from POS". Record this in DECISIONS.md, and add the follow-up: "post unapplied receipts to a suspense account on arrival".

## Part G — Tests

**Fakes:** use a **fake Daraja** (OAuth, STK push, STK query, Dynamic QR, C2B register) and the **real relay** in integration tests.

**Relay:**
- tenant isolation, as a security test
- only Safaricom IPs plus a valid token are accepted
- duplicate callbacks are stored once
- the hold-until-acknowledged behaviour, including a reconnect after an outage
- 30-day clean-up
- the API key is hashed

**Collection:**
- connected only while tickets are open
- catch-up at day open, before Close day, and on Fetch now
- nothing is lost across a disconnect

**STK:**
- phone normalisation
- the amount can't exceed what's remaining
- one active prompt per ticket
- the callback route, **and** the query route with the relay down
- each Daraja result code becomes its plain message
- success adds a pending payment with the right brought-by
- the cashier must still Complete
- the waiter's prompt follows the setting and permissions

**QR:**
- printed on the bill when on, absent when off
- Daraja slow or offline → the bill prints within 3 seconds without the QR (as a golden slip)
- exact reference matching (per the Part D finding)
- amount-only suggestions are never auto-applied

**Received and typed:**
- partial application across two tickets
- no change is given
- a typed code that arrives later is linked and confirmed
- after 24 hours it's flagged as never confirmed
- a code can be used only once across all sources

**Ledger:**
- the tiles add up to the rows
- Apply to ticket
- "not from POS" posts a balanced entry to the chosen account
- the Close day warning
- the export columns
- permissions

**Settings:**
- credentials are never returned by any API
- Test connection with each check passing and failing
- C2B URL registration is called with the relay paths
